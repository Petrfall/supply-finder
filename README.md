# Поиск поставщиков продуктов питания

Сервис помогает быстро **найти и сравнить поставщиков** food-направления
(ингредиенты, готовая продукция, упаковка) и понять, **с кем связаться первым**.

🔗 **Прототип:** _(добавить ссылку после деплоя)_
🧩 **Стек:** FastAPI + SQLite + React (TS) · Anthropic API (web search + structured output)

---

## Идея

Архитектор тратит часы на ручной обход сайтов и агрегаторов, чтобы собрать по
поставщику разрозненные данные (MOQ, цены, сертификаты, контакты) и сравнить их.
Сервис автоматизирует именно этот сбор и нормализацию:

1. Пользователь задаёт **категорию** и **город/регион** (+ фильтры).
2. Сервис находит поставщиков, **извлекает данные в единую строгую схему** и
   нормализует их.
3. **Детерминированный скоринг** ранжирует поставщиков по соответствию запросу и
   подсказывает, с кем связаться первым — с объяснением, *почему*.

## Как это работает

```
Запрос (категория + регион + фильтры)
   │
   ▼  POST /api/search
FastAPI
   ├─ 1. cache lookup (SQLite по hash запроса) ──► hit → отдаём мгновенно
   ├─ 2. provider:
   │      • Anthropic (live): web search → текстовый дайджест,
   │        затем отдельный structured-output вызов → Supplier[] (Pydantic)
   │      • mock (нет ключа): пусто → переходим к seed
   ├─ 3. seed fallback (если live пусто или ключа нет)
   ├─ 4. нормализация + дедуп (по домену/названию, слияние полей)
   ├─ 5. СКОРИНГ в коде (region/category/contacts/certs/MOQ/price/delivery)
   ├─ 6. краткая сводка «кого выбрать» + причина у топ-поставщика
   └─ 7. запись результата в кэш
   │
   ▼
React: карточки поставщиков + фильтры + таблица сравнения (RU/EN)
```

### Почему именно так (обоснование формата)

- **Скоринг считает код, а не модель.** Каждый балл прослеживается до правила
  (`backend/app/scoring.py`), и один и тот же запрос всегда даёт один результат —
  это аудируемо, в отличие от «модель сказала 87».
- **Provider-абстракция (Anthropic / mock).** Сервис **работает без API-ключа** в
  демо-режиме на seed-данных — HR открывает прототип и сразу видит результат.
  С ключом включается реальный веб-поиск. Тот же паттерн я использовал в
  [resume-scorer](https://github.com/Petrfall/resume-scorer).
- **Два шага: поиск → извлечение.** Веб-поиск Anthropic и structured output
  нельзя совместить в одном вызове, поэтому сначала модель ищет и пишет дайджест,
  потом отдельный вызов с `output_format` (Pydantic) извлекает данные в схему —
  гарантированно валидный JSON.
- **Кэш по хэшу запроса (SQLite).** Не платим за один и тот же поиск дважды;
  он же позволяет закоммитить «прогретые» запросы для офлайн-демо.
- **Source-attribution.** На карточке — ссылка на источник: прозрачность данных.

## Функциональность

- Поиск по **категории** и **городу/региону**.
- Фильтры: только с сертификатами, ключевое слово.
- По каждому поставщику: контакты, сайт/источник, **MOQ, цена, сертификаты,
  условия доставки, регионы поставки**.
- **Fit-score** + объяснение «почему этот».
- **Таблица сравнения** до 4 поставщиков бок о бок.
- Двуязычный интерфейс **RU / EN**.

## Запуск

### Через Docker (рекомендуется)

```bash
# опционально для live-поиска:
export ANTHROPIC_API_KEY=sk-ant-...
docker compose up --build
# фронт:    http://localhost:8080
# бэкенд:   http://localhost:8000/api/health
```

Без `ANTHROPIC_API_KEY` сервис работает в демо-режиме на seed-данных.

### Локально без Docker

```bash
# backend
cd backend
uv venv && uv pip install -r requirements.txt
uv run uvicorn app.main:app --reload          # http://127.0.0.1:8000

# frontend (в другом терминале)
cd frontend
npm install && npm run dev                     # http://127.0.0.1:5173
```

Vite в dev-режиме проксирует `/api` на бэкенд (см. `vite.config.ts`).

## Структура

```
backend/app/
  models.py      # Pydantic-контракты (Supplier, ScoredSupplier, запрос/ответ)
  providers.py   # Anthropic (web search + extraction) | mock — единый интерфейс
  scoring.py     # детерминированный fit-score по взвешенным сигналам
  dedup.py       # дедуп по домену/названию со слиянием полей
  cache.py       # SQLite-кэш по хэшу запроса
  seed.py        # демо-датасет RU-поставщиков (fallback без ключа)
  main.py        # FastAPI: /api/search, /api/health, сборка пайплайна
frontend/src/
  App.tsx        # форма поиска, карточки, сравнение, переключатель языка
  components/     # SupplierCard, ComparisonTable
  lib/           # api-клиент, типы, i18n (RU/EN)
```

## Что можно расширить

- LLM-обоснование «почему этот» на каждую карточку (сейчас — у топ-поставщика).
- Векторный поиск по накопленной базе поставщиков (pgvector/Qdrant).
- Экспорт сравнения в CSV/PDF, заметки по поставщику, история запросов.
- Дедуп по ИНН и обогащение из открытых реестров.
